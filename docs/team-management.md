# 团队账号与 Token 管理

## 角色分工

| 角色 | 用途 | 建议数量 |
| --- | --- | --- |
| Root | 系统设置、认证策略、角色权限 | 1 个，启用 2FA，平时不使用 |
| Admin | 用户、渠道、模型和日常运维 | 1～2 个，启用 2FA |
| User | 创建自己的 API Token、调用模型、查看自己的日志 | 每位成员 1 个 |

## 初次设置清单

Root 登录后：

1. 绑定邮箱，修改强密码，启用 2FA，并保存恢复码。
2. 系统设置 → 认证：关闭密码注册和 OAuth 注册。
3. 关闭团队不使用的充值、支付、签到和公开运营入口。
4. 将服务器/API 地址设为实际的 HTTPS 公网域名。
5. 创建 Admin，并只授予实际需要的管理权限。
6. 创建 User，初始配额按团队制度发放。

## Token 策略

成员登录自己的账号后创建 Token。推荐字段：

- 名称：`alice-codex-laptop` 这类能定位人员和设备的名称。
- 额度：设置合理上限，避免误调用耗尽团队资源。
- 模型：仅开放实际需要的模型。
- 有效期：临时成员和项目 Token 必须设置到期时间。
- IP 白名单：仅用于固定办公出口或稳定 VPN 网段。

同一成员的不同设备或自动化任务也可以使用不同 Token，便于单独撤销和定位日志。

## 入职与离职

入职：

1. Admin 创建 User，不发送 Root/Admin 账号。
2. 成员首次登录后修改密码并启用 2FA。
3. 成员自行创建 Token，管理员配置额度和模型范围。
4. 发起一次测试调用并确认日志归属正确。

离职或设备丢失：

1. 立即禁用用户或撤销对应 Token。
2. 撤销该用户所有登录会话。
3. 检查近期调用日志和异常额度消耗。
4. 只有 CPA 内部密钥泄露时才轮换 `CPA_API_KEY`；普通成员不应接触该密钥。

## 不应采用的做法

- 全团队共享一个 New API Token。
- 把 CPA API Key 直接发给成员。
- 日常使用 Root 账号。
- 为方便登录而开放公开注册。
- 在聊天软件、Issue、日志或截图中粘贴完整密钥。
